# Architecture Decision Records (ADRs)

Format: Context · Decision · Alternatives · Why · Trade-offs · Future reconsideration trigger.

---

## ADR-001 — Modular Monolith
**Context:** Scale is 1k–5k rows, single team, 5-minute demo, judged on completeness and clarity. **Decision:** One deployable FastAPI backend partitioned into modules (`ingestion, validation, exceptions, review, ai, verification, audit, consumer`) with enforced layering. **Alternatives:** Microservices; serverless functions. **Why:** Lowest operational complexity, fastest iteration, easy local run, clean internal boundaries still demonstrate architecture maturity. **Trade-offs:** Shared process/deploy; must self-discipline boundaries (import-linter later). **Reconsider when:** independent scaling/deploy of ingestion or validation is required, or team splits by domain.

## ADR-002 — PostgreSQL as primary store
**Context:** Relational lineage, JSONB for raw payloads/snapshots, strong constraints for invariants. **Decision:** PostgreSQL + SQLAlchemy + Alembic. **Alternatives:** SQLite (simpler), MongoDB (schema-flex). **Why:** Need transactional integrity (atomic snapshot+audit), unique constraints (`loan_id,version`), JSONB (raw + snapshot), and it matches the target prod. **Trade-offs:** Heavier local dep than SQLite → mitigated by Docker Compose. **Reconsider when:** never for this scale; sharding only far past it.

## ADR-003 — Deterministic validation is the source of truth; AI is advisory only
**Context:** PS §9 + business rules: AI must not silently mutate data. **Decision:** All exceptions/severity computed by a pure rule engine; AI writes only to `ai_recommendations`; humans apply changes via `review`. **Alternatives:** AI-in-the-loop validation. **Why:** Auditability, reproducibility, demo reliability, judging on human control. **Trade-offs:** Some duplication (AI may re-explain deterministic result). **Reconsider:** never — this is a core competition requirement.

## ADR-004 — AI Provider abstraction with a deterministic Mock default
**Context:** App must work if AI fails; tests/demo must be reproducible. **Decision:** `AIProvider` interface with `AnthropicProvider` and `MockProvider`; `AI_PROVIDER` env selects. Mock returns stable, fixture-based output. **Alternatives:** Direct SDK calls everywhere. **Why:** Testability, offline demo, provider swap, graceful degradation. **Trade-offs:** Extra interface layer. **Reconsider:** add providers as new impls; interface stays.

## ADR-005 — Verified records are immutable, versioned snapshots
**Context:** PS Module E + "future corrections create a new version." **Decision:** Append-only `verified_loans` with `(loan_id, version)` unique; snapshot JSONB + `record_hash`. **Alternatives:** Mutable current-verified row + history table. **Why:** Tamper-evidence, clean lineage, matches traceability scoring. **Trade-offs:** Storage growth (negligible at scale). **Reconsider:** prune only with legal/retention need (out of scope).

## ADR-006 — Synchronous processing; no task queue yet
**Context:** 5k rows validate in <1s in-process. **Decision:** Sync upload→normalize→validate in one request/txn; AI on-demand sync with timeout+fallback. **Alternatives:** Celery/RQ/arq worker. **Why:** Determinism, simpler demo, fewer moving parts, immediate summary. **Trade-offs:** Long request if files are huge. **Reconsider when:** files >100k rows or AI batch latency hurts UX → add `arq` + Redis (see scaling-strategy).

## ADR-007 — Canonical JSON hashing in one shared function
**Context:** File/row/record hashes must be reproducible by a judge. **Decision:** Single `core/hashing.py` with canonical serialization (sorted keys, normalized Decimal/date, excluded volatile fields), SHA-256. **Alternatives:** ad-hoc per-layer hashing. **Why:** Consistency, documented reproducibility. **Trade-offs:** Must freeze the canonicalization spec. **Reconsider:** version the canonicalizer if the schema changes post-verification.

## ADR-008 — Append-only audit with optional hash chain
**Context:** PS Module F (10 events) + traceability score. **Decision:** `audit_events` insert-only, written in same txn as the change; optional `prev_hash/event_hash` chain. **Alternatives:** app logs only; event sourcing. **Why:** Query-able history + tamper-evidence without event-sourcing complexity. **Trade-offs:** Chain adds a tiny write cost. **Reconsider:** full event sourcing only if audit becomes the system of record.

## ADR-009 — JWT role auth (demo-grade), roles seeded from users.json
**Context:** PS §16 lists production-grade security as out of scope; still need 3 working roles + test creds. **Decision:** Signed JWT, `require_role` dependency, users seeded from `users.json`. **Alternatives:** full OAuth/OIDC; session cookies. **Why:** Enough to demonstrate RBAC and the demo login flow; low complexity. **Trade-offs:** Not production hardened (accepted). **Reconsider:** real IdP if this leaves hackathon scope.

## ADR-010 — Vite SPA + TanStack Query + shadcn/ui, OpenAPI-typed client
**Context:** Fast, polished, role-based dashboards; strong UX weight (15 pts). **Decision:** React+Vite+TS SPA, TanStack Query for server state, shadcn/ui + Tailwind, types generated from backend OpenAPI. **Alternatives:** Next.js. **Why:** No SSR need; simplest static deploy; generated types keep FE/BE in sync. **Trade-offs:** Manual routing/SEO (irrelevant here). **Reconsider:** Next.js if SSR/SEO ever needed.

## ADR-011 — Rules & severity are config-driven (validation_rules.json)
**Context:** PS ships `validation_rules.json`; AI can "generate rules from NL." **Decision:** Rule engine reads a versioned ruleset (thresholds, severities, allowed-edit fields) from config; `ruleset_version` stamped on each run. **Alternatives:** hard-coded rules. **Why:** Configurable, versionable, lets AI rule-gen produce diffable proposals a human approves. **Trade-offs:** Slightly more indirection. **Reconsider:** move to DB-stored rulesets if runtime editing is needed.

# Reliability & Scale ADRs (Loop 3 — decided, most implemented in later slices)

## ADR-012 — Ingestion stays synchronous up to a measured trigger
**Context (Scenario 1, large file):** CSV of 1k–10k rows. A 10k-row parse + normalize + validate is well under a couple of seconds in-process; memory is bounded by streaming the CSV row-by-row rather than loading all rows as objects. **Decision:** Keep upload→normalize→validate synchronous in one request. Use SQLAlchemy `bulk_insert_mappings` / batched inserts (batch 1,000) for `raw_records` and `loans` so it's a handful of round-trips, not N. Return the import summary in the response. **Alternatives:** background worker now. **Why:** determinism, demo simplicity, no queue infra (avoids over-engineering). **Trade-offs:** a pathological >100k-row file would risk an HTTP timeout. **Future trigger:** import p95 >2s or file >100k rows → move ingestion/validation to an `arq`+Redis `worker` service (documented in scaling-strategy, NOT built now).

## ADR-013 — Duplicate upload = preserve evidence, reuse content, new logical upload
**Context (Scenario 2):** same file uploaded twice. **Decision:** Compute `file_hash` (SHA-256 of bytes). If a `source_files` row with that hash exists, do **not** silently reject and do **not** silently merge: create a **new `source_files` record** (new logical upload, own id/timestamp/uploader) but mark it `duplicate_of=<original_id>` and **skip re-inserting `raw_records`** (reuse the original evidence rows by reference). The API returns `409-style` info in the summary (`"duplicate": true, "original_upload_id": ...`) and the UI warns. **Alternatives:** hard reject (loses the audit that someone re-uploaded); allow full duplicate (wastes storage, creates phantom duplicate exceptions). **Why:** preserves the audit fact "this was uploaded again" while keeping raw evidence immutable and de-duplicated, and avoids polluting the exception queue with duplicate rows. **Trade-offs:** slightly more branching in ingestion. **Reconsider:** add a force-reingest flag if a legitimately changed file ever reuses a hash (impossible by definition) — n/a.

## ADR-014 — Validation runs are versioned & idempotent
**Context (Scenario 3):** validation triggered twice. **Decision:** Each run creates a `validation_runs` row stamped with `ruleset_version` and a `run_status`. Exceptions are keyed by a deterministic natural key `(loan_id, rule_id)` with a unique constraint so re-running **upserts** rather than duplicating. A new run supersedes the previous run's open exceptions for that loan (old ones marked `resolved_by_rerun`), so the queue never shows uncontrolled duplicates. Concurrent runs on the same `source_file_id` are guarded by a row lock / `run_status='running'` check. **Why:** re-validation is safe, traceable, and rule-version-attributable. **Trade-offs:** upsert logic is slightly more complex than blind insert. **Reconsider:** n/a.

## ADR-015 — Optimistic locking on reviewer-mutable rows
**Context (Scenario 5):** two reviewers resolve the same exception. **Decision:** Add a `version` integer to `exceptions` and `loans` (SQLAlchemy `version_id_col`). Write operations include the expected version; a stale write raises → API returns **409 Conflict** ("record changed, please refresh"). This is last-writer-**protected**, not last-writer-wins. **Alternatives:** pessimistic DB locks (heavier, deadlock risk); no protection (silent overwrite). **Why:** minimum correct protection for a low-concurrency app; cheap and standard. **Trade-offs:** the loser must retry. **Reconsider:** real-time collaboration would need locking/websockets — out of scope.

## ADR-016 — Critical multi-write operations share one transaction
**Context (Scenario 6):** decision+audit, snapshot+audit must not half-commit. **Decision:** Each service function that changes state and writes an audit event does both inside a single `Session` transaction (`with session.begin()`), so a DB failure rolls back the whole unit — no orphan audit events, no unaudited state changes. Verified-snapshot creation wraps snapshot+hash+audit atomically. **Why:** the traceability guarantee depends on audit-with-change atomicity (ADR-008). **Trade-offs:** none meaningful at this scale. **Tests:** `test_verify_atomic`, `test_decision_atomic` (added with the relevant slices). **Reconsider:** an outbox pattern only if audit ever moves to a separate store (not planned).

## ADR-017 — AI failures are recorded, never fatal
**Context (Scenario 4):** AI times out / returns invalid JSON / unavailable. **Decision:** Every AI call runs with a timeout (`AI_TIMEOUT_SECONDS`); output is validated against a Pydantic schema; any failure returns a structured degraded result (`degraded: true`) and writes an `ai_audit_logs` row with the failure reason — canonical loan state is untouched, human review continues. Mock provider is the default so the demo never depends on the network. **Why:** PS §9 + business rule "app usable if AI fails." **Trade-offs:** none. **Tests:** `test_ai_output_schema`, degradation test (AI slice). **Reconsider:** add a short per-(loan,kind) cache if latency/cost ever bites (documented, not built).

## ADR-019 — Deterministic synthetic bootstrap dataset (real sources are gated)
**Context (Phase 1):** the organizer package is not shipped in the repo, and the PS's public sources (Fannie/Freddie) are registration- and terms-gated — not fetchable non-interactively. The PS itself recommends a synthetic dataset for judging. **Decision:** ship `scripts/generate_synthetic_dataset.py` — a **deterministic** (fixed seed + fixed `as_of`) generator that emits organizer-shaped files (`loan_tape.csv` 1,000 rows, `servicer_update.csv`, `document_manifest.csv`, `validation_rules.json`, `expected_exception_sample.csv`) conforming to PS §6 and embedding all 15 PS §7 issue classes, with a ground-truth exception ledger. `scripts/download_datasets.py` accepts `--organizer-dir` to drop in the real package when available (never overwriting without `--force`); `profile_datasets.py`/`verify_datasets.py` fingerprint everything into `data/manifest.json`. **Alternatives:** hand-craft a tiny CSV (too small to demo scale); require manual download (not reproducible; blocks judges). **Why:** reproducibility, immediate runnability, deterministic hashes/demo, honest about the gated sources, and it doubles as the validation golden set. **Trade-offs:** synthetic ≠ real distributions; the `interest_rate` unit convention is UNCONFIRMED (see data-contract). **Reconsider/replace:** when the real organizer file arrives, `download_datasets.py --organizer-dir … --force` + re-profile; the field contract is unchanged, only example values/counts differ.

## ADR-020 — Field provenance as embedded JSON on the canonical loan (not a separate table)
**Context (Phase 3):** need per-field lineage (raw value → transformation → canonical value → status) for all 21 fields, for Traceability scoring. The Phase 3 brief names a `LoanFieldProvenance` entity. **Decision:** realize it as a structured `field_provenance` JSON column on `loans` (+ a `normalization_status` clean|attention column), written once at import — NOT as a `loan_field_provenance` table (which would be 21 rows/loan = 21k–105k rows per import). **Alternatives:** dedicated per-field table. **Why:** a table would multiply import write-volume ~21× and push the synchronous-import budget (ADR-012) toward its async trigger at 5k rows, for no current benefit — there is no cross-loan provenance *query* requirement yet. Embedded JSON delivers full per-field lineage (exposed via `GET /loans/:id.field_provenance`, filtered via `GET /loans?attention=true`, and `issue_fields` in list rows) at 1 write/loan. This supersedes the earlier "JSON-first, promote later" note in the entity-contract review — the decision is now explicit. **Trade-offs:** can't SQL-filter *within* provenance across loans (only the derived `normalization_status` is indexed). **Promotion trigger:** build the table when a real cross-loan provenance query appears (e.g. "every loan where interest_rate was coerced"). **Immutability:** written once at normalization; reviewer edits later create audited decisions, not provenance rewrites.

## ADR-018 — Request-ID + structured access logging; /health & /ready aliases
**Context:** traceability of requests; spec asks for `/health`. **Decision (implemented Loop 3):** middleware assigns/propagates `X-Request-ID`, binds it to a contextvar surfaced in every JSON log line, and emits one structured access log per request (method, path, status, duration_ms). Added `/health` + `/ready` as aliases of `/healthz` + `/readyz`. **Why:** cheap, benefits every future slice, spec compliance. **Trade-offs:** none. **Reconsider:** ship logs to an aggregator only in a real deployment.
